# Git Conflict Resolution Guide

You are helping resolve git conflicts during a {{operation}} operation.

## Workflow

1. **Assess the situation**
   - Use `git-hex-getConflictStatus` to see all conflicting files and their state
   - Review which files have conflicts and their content types

2. **For each conflicting file**
   - Read the file to understand the conflict markers (`<<<<<<<`, `=======`, `>>>>>>>`)
   - Determine the correct resolution:
     - **ours**: Keep the current branch version
     - **theirs**: Keep the incoming changes
     - **manual**: File needs manual editing (edit first, then use `manual`)

3. **Resolve conflicts one at a time**
   - Use `git-hex-resolveConflict` with the appropriate resolution strategy
   - Verify each resolution before moving to the next file

4. **Continue the operation**
   - Once all conflicts are resolved, use `git-hex-continueOperation`
   - If you need to abort instead, use `git-hex-abortOperation`

## Best Practices

- Always read conflicting files before choosing a resolution strategy
- When in doubt, prefer `manual` resolution after editing
- Keep the user informed about what changes you're making
- If {{conflictCount}} is large, consider aborting and trying a different approach

## Available Tools

- `git-hex-getConflictStatus`: List all conflicts and their state
- `git-hex-resolveConflict`: Resolve a single file conflict
- `git-hex-continueOperation`: Continue after all conflicts resolved
- `git-hex-abortOperation`: Abort and restore previous state

## LLM Decision Guide

**Conflict types and resolutions**:
| Conflict Type | Meaning | Typical Resolution |
|--------------|---------|-------------------|
| `both_modified` | Both branches changed same lines | Edit file to merge changes, then `resolveConflict` |
| `deleted_by_us` | We deleted, they modified | `resolution: "keep"` to restore, or `"delete"` to confirm deletion |
| `deleted_by_them` | They deleted, we modified | `resolution: "keep"` to keep our version, or `"delete"` to accept deletion |
| `added_by_both` | Both branches added same file | Edit to merge content, then `resolveConflict` |

**Step-by-step resolution**:
1. Call `git-hex-getConflictStatus` with `includeContent: true` to see file contents
2. For each conflict:
   - Show user the `base`, `ours`, and `theirs` versions
   - Help them decide what the merged result should be
   - If content conflict: user edits file to remove markers, then call `resolveConflict`
   - If delete conflict: call `resolveConflict` with `resolution: "keep"` or `"delete"`
3. After all files resolved, call `continueOperation`
4. If new conflicts appear (multi-commit rebase), repeat from step 1

**When to suggest abort**:
- User is overwhelmed by number of conflicts
- Conflicts are in generated or vendored files
- User wants to try a different rebase strategy
- The rebase is changing too much history

**Never do**:
- Call `continueOperation` while conflicts remain (will fail)
- Assume what resolution user wants for content conflicts
- Silently choose `delete` for delete conflicts without asking
